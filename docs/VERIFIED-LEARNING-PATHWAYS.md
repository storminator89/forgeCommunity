# Private Verified Learning Pathways

A pathway is an administrator-curated, immutable recommended order of two to four distinct courses. Creation requires each course to be published, free under the existing enrollment rule (`price` absent or at most zero), reward-approved for its current material, and to contain a valid rewardable quiz. The definition saves the ordered course IDs and title snapshots; it does not enroll anyone or change payment behavior. Definitions have no edit or delete API. A one-time seal and database guards reject later edits or course insertion, including SQLite replacement writes. Creation locks the selected course rows through sealing (a SQLite writer lock or schema-qualified PostgreSQL row locks) against concurrent deletion and approval/publication writes. Later removed or unpublished courses make the pathway unavailable: new members do not see it, new joins and rejoins return 409, existing participants retain their private definition, credit and badge history, opt-out remains available, and dead course links disappear. Unpublication can be reversed; deletion leaves an unusable slot under this contract. Administrators can still see its unavailable state. Approval withdrawal without unpublishing keeps the pathway discoverable and explains revalidation. A separate future retirement/archive contract is needed if administrators should remove now-impossible pathways from their administrative view without erasing history.

A normal, non-test `USER` may opt in, opt out, or rejoin while all recommended courses remain available. The unique `(userId, pathwayId)` participation survives opt-out; opt-out does not delete history or course learning. Pathway participation does not enroll anyone in a course. Each available, free unenrolled course has an explicit course-join action through the existing idempotent enrollment API before opening its contents. A full course returns 409 with a visible retry-later message; it does not create pathway credit. Badge state is private to this participation and is never written to `UserBadge` or projected into public profiles, search, rankings or participant lists. There are no pathway points, streaks, deadlines, notifications, public ranks or penalties.

Progress comes solely from the learner's *currently active*, server-owned `RewardLedger` rows with event type `COURSE_COMPLETED`, one distinct course per ordered pathway slot. The pathway order is a recommendation, not chronological gating: a course completed before joining or earlier in a different order counts if its reward is still current. Per-course prerequisites remain independently enforced. Historical `CourseCompletionRecord`, `Enrollment.completedAt`, client-supplied progress, and old quiz attempts cannot grant credit. The existing reward eligibility check remains authoritative: current completion and passing current server-graded quiz, enrollment, normal non-test account, non-instructor status, and administrator approval of current quiz/assignment material. Revocation means the current learning or approval condition changed, not misconduct. The pathway badge appears after all slots have active credit. Current reward loss or opt-out revokes it; restoration of every current reward or rejoining reinstates the same unique badge state. A versioned, append-only audit records AWARDED, REVOKED and REINSTATED. Transactions use conditional version updates, unique keys and serializable reward/participation operations to make retries and duplicate joins idempotent.

The shared reward reconciler drives pathway reconciliation after award, revocation and reactivation; batch revocation covers approval withdrawal and course deletion; account reconciliation covers role/test-account changes. Quiz edits, assignment grading withdrawal or material revisions reach the same hook. The normal free-course unenrollment endpoint refuses to remove a completed enrollment, so an already rewarded learner cannot silently lose enrollment through that route. These hooks do not change the reward ledger, certificate or paid-course policy.

Private API contract:

- `GET /api/learning-pathways/me`: `{ pathways: [...] }`, current normal member only.
- `POST /api/learning-pathways/:pathwayId/participation`: idempotent join/rejoin, `{ pathway }`, 201 on first join and 200 on repeat/rejoin.
- `DELETE /api/learning-pathways/:pathwayId/participation`: idempotent opt-out, `{ pathway }`, 200.
- `GET /api/admin/learning-pathways`: sealed definitions only, `{ pathways: [...] }`, current administrator only.
- `POST /api/admin/learning-pathways`: `{ requestId: UUIDv4, title, description, badgeLabel, courseIds: [2–4 ordered distinct IDs] }`; rechecks the current administrator and every current course condition in the creation transaction; returns `{ pathway }`, 201. An exact same-administrator, same-payload retry with the same `requestId` returns the original sealed pathway and 200, even after a lost response. Reusing the ID with changed fields or course order returns 409. The browser keeps the UUID for failed submissions of an unchanged draft and generates a new one after a change or success.

A member pathway has `id`, `title`, `description`, `badgeLabel`, `unavailable`, `courses: [{ courseId, title, order, available, isEnrolled, creditActive }]`, `requiredCount`, `creditedCount`, `participation: null | { joinedAt, optedOutAt, badgeActive, badgeFirstAwardedAt }`, and up to 20 newest `history: [{ type, reason, at }]` changes. Revocation reasons are `REWARD_INVALIDATED`, `OPTED_OUT`, and `ACCOUNT_INELIGIBLE`. Administrative definitions omit participation, credit, history and members but include `unavailable`. The member role check, course availability, enrollment, badge state and current ledger credits are read within one serializable snapshot. Every pathway response, including errors, carries `Cache-Control: private, no-store`; user identity is derived from the authenticated session and checked against the stored account role. All creation and participation mutation handlers apply the existing same-origin request guard before authenticating or writing. No endpoint accepts progress, badge, award or recipient fields from the client.

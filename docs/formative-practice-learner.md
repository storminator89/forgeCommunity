# Formative practice learner engine (first cut)

This adds private, optional recall practice for enrolled learners. It is separate from credential quizzes. It never writes `QuizAttempt`, credential grades, `CourseContentProgress`, prerequisites, rewards, certificates, or public scores. There are no individual instructor analytics or learner leaderboards.

## Availability and version boundary

A course begins with practice **off** because it has no published practice snapshot. Publishing a practice snapshot against the active `CoursePublication` makes practice available. Every learner still must explicitly opt in; `POST start` cannot opt in. The active learner pool is the latest immutable `PracticeSnapshot` whose `courseId` and `coursePublicationId` equal the course and its current `activePublicationId`. No fallback to a snapshot from an earlier course publication is allowed. A newly published practice snapshot supersedes an older one even if the credential publication did not change.

Before serving a reserved item or grading an answer, the server checks its copied payload against the pinned immutable `PracticeItemRevision`. Practice content never reads from `QuestionBankItem` or `QuizQuestion`. Revisions and their schedule keys are versioned by snapshot, item ID, and item revision; republishing creates a fresh private schedule namespace. Old evidence remains private until retention or an explicitly confirmed reset. A stale session cannot select or newly answer an item; an exact unexpired idempotency replay remains possible.

## Learner API

All routes are under `/api/courses/:courseId/practice/learner`, require a database-verified course enrollment and the current signed-in user, and return `Cache-Control: private, no-store` on success and error. Instructor/administrator roles alone confer no learner access. `401` means no session; `403` means no enrollment; `404` means no course or owned session; `409` means a paused, stale, unavailable, already answered, or conflicting state; `400` means invalid input.

- `GET /` is read-only. It returns `{status, dueCount, publicationId?, snapshotId?, session?}`. A session contains `{id, answeredCount, pending?}`. `pending` contains `{reservationId, ordinal, item:{itemId,itemRevision,objectiveTitle,prompt,options}}` only after an explicit reservation. This GET never returns an answer key or explanation and never marks an item as shown.
- `POST /opt-in` explicitly sets `optedIn=true` and unpauses. It preserves prior private history. `POST /pause` stops new selections and answers without deleting data. `POST /opt-out` disables practice without deleting data.
- `POST /start` requires prior opt-in and reserves the first item in a new session, or resumes the active session. `POST /next` with `{sessionId}` is the learner's deliberate continue action. Repeating either while a reservation is unanswered returns that same reservation without recording another showing. They return `{sessionId,answeredCount,pending?,complete}`. `complete=true` means no eligible due item or the 10-answer session cap was reached. The final answer in an exhausted or 10-answer session closes that session transactionally, so leaving before pressing Next cannot strand later reviews. A pre-existing exhausted active session can be closed by an explicit Next action in the learner UI.
- `POST /answer` accepts `{sessionId,reservationId,submissionId,optionIndex,confidence?}`. Confidence is `SURE`, `SOMEWHAT_SURE`, `UNSURE`, `GUESSED`, or omitted/null. It returns `{correct,correctIndex,explanation,nextDueAt,canContinue,answeredCount,replay}`. This neutral corrective feedback is practice-only and is provided after the answer is recorded. The submitted option, correctness, and optional confidence are private.
- `POST /reset/prepare` returns a random one-use token valid for 10 minutes. `POST /reset` requires `{token,confirmation:"RESET_MY_PRACTICE"}`. It deletes that learner's private practice sessions, answers, receipts, schedule, and opt-in for this course through a single transaction. The UI must ask for separate explicit confirmation before calling it. Pause and opt-out never invoke reset.

`status` is `unpublished` when the course has no active course publication; `off` when it has no practice snapshot; `archived` when practice exists only against an earlier course publication; `available` when the current snapshot exists but this learner has not opted in; `paused` when opted in and paused; `ready` when opted in with due items and no active session; `active` with an active session; and `complete` when opted in but no eligible due item is available now. The `pending` item returned by GET is an already reserved item for resuming a session, never a new reservation.

## Selector and idempotency

Selection is bounded by the published snapshot's maximum 100 items and at most 10 answered items per session. Due items sort by earliest `dueAt`, then byte-stable item ID for ties. The last two shown within the previous 24 hours and all items already shown in the same session are excluded. This prevents immediate repetition while allowing a small pool to become available again after a day. Unseen items are due immediately. A correct answer raises a bounded streak and schedules 1–30 days later; `SURE` doubles the interval to a 30-day cap, and `UNSURE`/`GUESSED` schedule six hours later. An incorrect answer is due in 10 minutes, or five minutes when confidently wrong, subject to the no-repeat window. Confidence changes only private review timing.

`submissionId` is scoped to a session. The server transaction writes one answer per reservation and an idempotency receipt. Repeating the same ID and body within 90 days replays the recorded outcome, including whether another item could be opened; reusing that ID with a different body fails with `409`. A new ID cannot grade an answered reservation. After the receipt is purged, durable answer/reservation uniqueness still rejects a late duplicate rather than grading twice. Serializable transactions, a partial unique active-session index, unique reservation constraints, and version-based compare-and-swap make concurrent starts and answers resolve to one reservation and one answer. Errors roll back the entire selection or answer; no item is silently consumed on failure.

## Retention and operation

An inactive learner setting and its cascading private history/schedule become eligible for deletion after **12 calendar months without learner practice activity**. Technical answer-submission idempotency receipts become eligible after **90 days**. These are eligibility thresholds, not promises of deletion at an exact instant. GET does not count as activity; opt-in, pause, opt-out, reservation, and answer do. Pause or opt-out preserves private data during the retention window. A separately confirmed reset immediately removes that learner's course-specific practice data, including receipts.

`npm start` and the Docker image start the retention scheduler after the reviewed database migration/readiness gate and **before** starting the HTTP server. Startup completes an initial catch-up sweep; it refuses to serve if readiness or the sweep fails. Subsequent ticks run every 15 minutes, with at most 20 batches of 500 settings and 500 receipts per tick. A backlog or transient failure schedules another attempt after 60 seconds. Each batch runs in a serializable transaction, rechecks both cutoffs when deleting, and records a successful database heartbeat only when caught up. PostgreSQL uses a fixed transaction-scoped advisory lock after validating the active custom schema; SQLite obtains a writer lock before selecting candidates. Competing ticks either serialize or retry, without double-deleting. Logs contain aggregate counts and a restricted error code, never learner identifiers or SQL values.

Before opt-in, start, next, or a new answer writes private practice data, the API requires a successful retention heartbeat from the previous 45 minutes. A missing, stale, or future-dated heartbeat returns 503 without writing. Private GET, pause, opt-out, reset, and an exact answer idempotency replay remain usable. A deployment that runs `next start`, `npm run start:standard`, `next dev`, or the standalone `server.js` directly does not start the scheduler: learner writes fail closed once a heartbeat is absent or stale. Production should use `npm start` or the Docker entrypoint/CMD, not those alternate server commands. The database credentials and provider/schema URL must be the same for the worker and app. Monitor recurring `practice_retention` aggregate tick/error logs and alert if no successful tick appears for 45 minutes; restore the worker rather than bypassing the gate.

`lib/server/formative-practice-retention.ts` retains a dry-run-by-default inspection hook, which never schedules a job. The scheduler's apply path is restricted to the server process and has no learner API. Implementation and tests used only disposable local databases; no existing or production learner data was deleted. Back up and verify restore procedures before deployment because production startup will delete records that are already retention-eligible. The disposable SQLite integration covers concurrent ticks, restart, heartbeat, and migration checksum fail-close. The PostgreSQL custom-schema release gate covers the corresponding PG path in CI.

The migrations are additive: SQLite `0016_formative_practice_learner.sql`, PostgreSQL `0015_formative_practice_learner.sql`. The fresh-install release allowlists require the exact reviewed sequence and checksums. This release continues the project's existing fresh-install-only deployment policy; it does not migrate a populated legacy database automatically.

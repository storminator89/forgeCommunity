## Scope and UI

`/admin/authentication` uses the existing current-ADMIN layout and a client form. Its two API methods independently authenticate. GET also calls `readAsAdmin` and reads the optional configuration in the same serializable authority snapshot. A missing PostgreSQL table aborts that read transaction; a fresh authority-only snapshot is required before returning a schema blocker. Passwords, provider secrets, hashes, fragments and ciphertext never appear in the public projection, HTML or error messages. Request bodies and provider configuration are never logged.

GET `/api/admin/oauth-configuration` returns only revision, blockers/canSave, source, callback URLs and non-secret provider settings plus secret-presence booleans. PUT accepts the documented form contract with `expectedRevision`. Null creates revision 1; each successful save increments once. A serializable transaction rereads the current ADMIN role and the credentials-session password fingerprint, reads the expected revision and performs a revision-conditioned update. On PostgreSQL the role/password are read by a parameterized SELECT FOR UPDATE against the same schema-qualified User table as PrismaPg, holding that actor row through commit so a demotion/password change cannot commit between authority check and settings write. SQLite uses its own serializable stale-snapshot/write-conflict path; no PostgreSQL locking SQL is sent to it. Duplicate creation, serialization conflicts and mismatched revisions return fixed HTTP 409 errors. The existing bounded in-process limiter is used with a dedicated admin-write policy; its existing single-instance limitation remains.

PUT requires a present Origin exactly matching canonical NEXTAUTH_URL.origin, rejects cross-site Fetch Metadata, accepts JSON only, and bounds the body at 24 KiB. Input objects are strict. Limits are name 60, ID 1024, secret 4096 characters and five additional HTTPS endpoint origins. Main's pre-existing environment validator still accepts up to sixteen additional origins, all of which the form can display. OIDC URL validation retains Main's public-HTTPS hostname restrictions, fixed code flow, validated discovery endpoints and five-second timeout.

Blank or omitted secrets retain only a secret from the existing decrypted database row. They never silently import environment secrets. An enabled provider on the initial environment-to-database save therefore requires a fresh private secret input. A saved database configuration completely replaces environment provider settings, including explicit disable. Disabled providers may retain their private database secret for later re-enabling. There is no secret-reveal route.

## Host prerequisites, key and migration

Before any later rollout, separately confirm and authorize the actual Main database/provider and its backup, review the two additive migrations in `OAUTH_CONFIGURATION_MIGRATION.md`, and provision:

- Canonical origin-only NEXTAUTH_URL (HTTPS in production)
- Existing independent NEXTAUTH_SECRET, at least 32 characters, for sessions
- A new independent `OAUTH_CONFIG_ENCRYPTION_KEY`: exactly 32 random bytes, encoded as standard Base64 (padded) or Base64url (unpadded or padded)

Generate/provision this key through the operator's secure secret-management process. It is not editable, readable or returned by the UI. Do not paste it into chat, source control, CI output or a UI field. Do not reuse NEXTAUTH_SECRET. Never rotate or replace it without a separately reviewed re-encryption/recovery plan: existing rows are intentionally unreadable under a different key. Back up both database and independent key under appropriate, separate access controls. No secret is bundled or generated by this candidate.

The encryption uses the official direct dependency `jose` 6.2.12, compact JWE with strict `dir`/`A256GCM` decryption allowlists and an exact protected type. The authenticated envelope binds purpose, format, Main stack, public origin, singleton ID and revision. Main ciphertext cannot be transplanted from Sites, another host, another row or a different revision. This is confidentiality/integrity against database-only disclosure/tampering, not protection from a compromised application host. Rolling back an entire database and key backup can roll back the row's revision; external rollback detection is not implemented.

Missing/invalid encryption key, missing schema, missing/invalid base URL and missing/invalid NEXTAUTH_SECRET block saving. Codes are `encryption_key_missing`, `encryption_key_invalid`, `schema_missing`, `base_url_missing`, `configuration_unavailable`. No successful activation is claimed without genuine later provider credentials and separately authorized live functional checks. GET may still describe existing environment login before bootstrap.

Both new SQL files currently live in the isolated candidate's active Main migration directories. They have not run. A later explicitly approved regular upgrade through db:deploy discovers them; the existing SQLite Docker startup migration runner also discovers and applies pending migrations. This preparation does not authorize deployment, startup or any database work. The optional OAuth extension does not introduce a new manual-migration requirement for the existing Main application's ordinary startup: the global readiness guard accepts all required predecessor receipts either with or without exactly the one known OAuth receipt. If that optional receipt exists, its checksum must match. All other missing, unknown, duplicate or divergent receipts still fail. Global readiness never reads or requires OAuthConfiguration. A missing table blocks OAuth settings writes with schema_missing and retains the established environment OAuth fallback and credentials/application startup behavior. Main and Sites remain separate stores.

## Runtime isolation and failures

All OAuth configuration is loaded into a request-local immutable-by-convention snapshot. No process.env or global provider/callback state is changed. The existing credentials provider, authorize function, JWT/session callbacks, roles, password invalidation, safe redirect behavior, CSRF handling, code-only callback checks and sign-in query normalization remain unchanged. authOptions used by session/credentials routes contains only credentials; the auth route injects the current optional providers per request. `/api/auth/providers` reflects the database configuration. Unexpected optional-store failures disable only OAuth; credentials remain available. Only a conclusively missing optional table or absent singleton permits the original environment fallback. An existing row with a missing key, decrypt error, incompatible envelope or database failure never falls back to environment providers.

The installed NextAuth v4 implementation reads custom state, nonce and PKCE names and also uses each name as its JWT salt. This candidate changes those three names using a domain-separated HMAC keyed by NEXTAUTH_SECRET over source plus the private environment snapshot or database revision/ciphertext binding. It exposes no unkeyed provider-secret hash, ciphertext or secret fragment. This covers environment changes across restarts and database revision changes while retaining secure/httpOnly/lax/path and 15-minute expiry. Session and CSRF cookie names are unchanged. Saving a revision invalidates previously started OAuth handshakes at cookie validation. The callback's signIn guard also rereads the current configuration revision and provider state before account lookup/link decisions.

## Identity safety and explicit framework limit

Existing Google subject identities and Main's SHA-256 of [exact OIDC issuer, subject] stay unchanged. Verified boolean email is still required. No email auto-linking or signed-in account-link flow was introduced.

Changing the configured OIDC issuer or client ID while an `oidc` Account exists returns HTTP 409 with exactly `oidc_identity_migration_required`. This is a separate deliberate identity-migration decision, not a field edit. The check and versioned settings update share the serializable transaction. PostgreSQL takes a namespace-correct table lock against Account inserts before its first MVCC read, so the following snapshot includes all earlier committed links; SQLite uses its serializable stale-snapshot/write-conflict behavior. There are no automatic account rewrites or deletes.

Main still uses NextAuth's own non-atomic multi-step finalization after the signIn callback. A configuration change observed before cookie/guard validation is rejected, but a save that commits after the last guard and before framework finalization cannot be guaranteed to abort that already in-flight framework operation atomically. Likewise an account created only after a settings transaction's account check is outside its historical snapshot. No framework-wide transaction engine or atomic revocation guarantee is claimed. A later request for stronger cancellation semantics requires an explicit architecture/scope decision.

### SQLite concurrency evidence (static, not executed)

The installed `@prisma/adapter-better-sqlite3` 7.10.0 implementation at `dist/index.js` 633–647 checks the supported isolation level and starts its transaction with `BEGIN`; the transaction owns its connection under the adapter's mutex. The configuration route reads authority/config/accounts and writes the singleton inside that same Prisma transaction. Main's SQLite initialization enables WAL. The official [SQLite isolation documentation](https://www.sqlite.org/isolation.html) explains that a WAL reader cannot become a writer after another connection commits a newer snapshot: escalation fails with `SQLITE_BUSY_SNAPSHOT` and requires rollback/restart. Rollback-journal mode also serializes writers against active readers. Accordingly a stale authority or account-count snapshot cannot later commit the settings write on this path. No SQLite concurrency test or SQL statement was executed in this preparation; deployed adapter/database behavior has not been functionally validated.

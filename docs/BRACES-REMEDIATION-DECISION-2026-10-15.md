# `braces` remediation decision, 15 October 2026

## Decision and evidence boundary

Keep the existing `security-audit` job and required `validate` aggregate unchanged. The integration lock inspected at `385b2ad6` contains `braces@3.0.3`, and the published [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) covers versions through 3.0.3 with **no patched release** listed. This is a current release gate, not a finding that can be called fixed by another successful quality check. A separate fresh local registry audit was denied during the earlier review; this assessment did not rerun it or try another local audit route. The ordinary authorized GitHub CI audit remains the acceptance signal on a published candidate.

The source and lockfile show these independent paths:

| Root declaration | Locked path to `braces@3.0.3` |
| --- | --- |
| `tailwindcss@^3.4.17` (dev dependency, locked at 3.4.19) | `tailwindcss` → `chokidar@3.6.0` → `braces`; also `tailwindcss` → `micromatch@4.0.8` → `braces`, and `tailwindcss` → `fast-glob@3.3.2` → `micromatch` → `braces` |
| `eslint-config-next@16.3.8` (dev dependency) | `eslint-config-next` → `@next/eslint-plugin-next@16.3.8` → `fast-glob@3.3.1` → `micromatch@4.0.8` → `braces` |

These edges are in `package-lock.json`; Next's [v16.3.8 ESLint plugin manifest](https://github.com/vercel/next.js/blob/v16.3.8/packages/eslint-plugin-next/package.json) independently confirms its exact `fast-glob@3.3.1` dependency. As of this review, even the [Next canary plugin manifest](https://github.com/vercel/next.js/blob/canary/packages/eslint-plugin-next/package.json) still specifies `fast-glob@3.3.1`. A Tailwind-only update therefore leaves the Next branch. Updating only Next or its config leaves Tailwind 3's several branches.

`eslint-config-next` is loaded by `eslint.config.mjs`; `@next/eslint-plugin-next` uses `fast-glob` in its `get-root-dirs` utility for the `no-html-link-for-pages` rule when a `settings.next.rootDir` glob is provided. The repository has no such setting. Tailwind is loaded through `postcss.config.js` for styling at build time. A source search found no direct application import of `braces`, `micromatch`, or `fast-glob`. Both root packages are declared in `devDependencies`, but the hoisted `braces`, `micromatch`, `chokidar`, and `tailwindcss` lock entries are **not** marked `dev: true`. No current integration standalone artifact was inspected, so this is **not** a verified production non-reachability claim. It does not change the all-dependencies CI audit. An artifact-level dependency inventory and runtime input-path review are required before making any stronger statement.

## Why small substitutions do not pass review

* `braces@3.0.3` is already the newest version shown by the advisory; overriding its version to the same value changes nothing. There is no advisory-recognized patched version to select today.
* Tailwind's [official v3→v4 guide](https://tailwindcss.com/docs/upgrade-guide) requires the separate `@tailwindcss/postcss` plugin, CSS `@import "tailwindcss"`, explicit `@config` for existing JavaScript config, and review of changed utility and Preflight semantics. Its v4 browser floor is Safari 16.4, Chrome 111, and Firefox 128. This project currently tests Chromium only; accepting that browser floor is a product decision. Tailwind 4 alone cannot fix the Next lint path.
* Replacing only `eslint-config-next` with direct `@next/eslint-plugin-next` does not remove `fast-glob`: the dependency belongs to the official plugin itself. The generic React, Hooks, import, JSX-accessibility, and TypeScript ESLint packages can reproduce their respective layers, but they do not implement the 22 enabled Next-specific rules. Dropping the official plugin would lose the framework lint checks, including `no-html-link-for-pages` and `no-sync-scripts` elevated to errors by Core Web Vitals. See the [Next ESLint reference](https://nextjs.org/docs/app/api-reference/config/eslint) and the installed `eslint-config-next`/plugin configurations.
* A direct npm alias from `fast-glob` to `tinyglobby` is not safe as a drop-in. Both export `globSync`, but a same-options local comparison returned different directory matches: `globSync('.', { onlyDirectories: true })` yielded `["."]` in `fast-glob` while `tinyglobby` traversed many child directories; an absolute directory likewise differed in path form and scope. The Next plugin's current default avoids this call, but a global alias would silently change its documented `rootDir` contract. A verified adapter or an upstream migration is needed. No custom glob/parser implementation or audit exclusion is recommended.

## Complete routes that preserve the gate

**Route A: adopt an upstream remediation.** When the advisory lists a published patched `braces` version compatible with the parents, update the lockfile (and parent ranges if needed), install from a clean checkout, then run the full matrix below. If a maintained Tailwind and Next plugin release instead both remove the affected package, update both and verify that the lock actually contains no affected `braces`. A discussion, unreleased main branch, or canary label alone is not a released fix. Revisit on a patched advisory entry or published parent release with changed dependency metadata; check actual CI on the exact revision. This is the lowest semantic and visual risk route, but no such release was verified on 15 October.

**Route B: independently reviewed dual-tool migration, if release timing requires it.** Migrate the UI to supported Tailwind v4/PostCSS while preserving all theme tokens, dark-mode behavior, plugin animations, custom layers, and generated utility coverage. Independently preserve Next lint semantics by taking a version-pinned, internally owned source fork of the official `@next/eslint-plugin-next` package, changing only its `fast-glob`-using root-directory utility to a supported glob library with a tested compatibility adapter, removing `fast-glob` from that fork's manifest, and pointing the lockfile's exact plugin dependency to that checked-in package. Keep `eslint-config-next/core-web-vitals` and the plugin's 22 rules and severities unchanged; test the default and explicit path/glob/array `rootDir` contract against the original package. This is a maintenance obligation, not an upstream-supported Next package. Rebase or retire the fork as soon as an official Next release drops the affected dependency. Do not silently remove the plugin, replace its glob function with an unreviewed parser, or claim audit success before CI.

Route B needs a separate design/compatibility acceptance before implementation: confirm the v4 browser floor; establish a baseline of screenshots and built CSS on the current UI; then make and review one Tailwind migration and one lint-fork migration, ideally as separately testable commits. The app uses custom HSL tokens, `tailwindcss-animate`, `@apply`, dark mode, `ring-offset-*`, border defaults, and at least one `transition-[...,transform]` class. The [Tailwind upgrade guide](https://tailwindcss.com/docs/upgrade-guide) identifies changes to border/ring defaults, transforms, hover behavior, and variant order; these may be visible or interactive regressions. `scripts/check-color-contrast.js` imports `tailwindcss/colors`, so verify its API and the light/dark contrast results after migration. If v4 browser compatibility is unacceptable, do not start Route B and continue pursuing Route A or a different fully supported styling toolchain. Planning estimate: multiple engineering days plus route-by-route visual QA, rather than a safe one-line dependency bump.

| Lint layer in current `eslint-config-next/core-web-vitals` | Direct-package replacement assessment |
| --- | --- |
| React and React Hooks recommended rules | Their official plugins can provide equivalent rules, with explicit parity testing of config and severities. |
| Import, JSX accessibility, TypeScript parser/resolver, globals | Direct packages can be configured, but all Next defaults and overrides must be copied and regression-tested. |
| 22 Next-specific recommended rules, two promoted to errors for Core Web Vitals | Direct official `@next/eslint-plugin-next` retains these rules **and** its `fast-glob` dependency. Generic plugins do not provide Next-specific parity. Retain the official plugin package until an upstream fix, or use the narrow reviewed internal fork described above. |

Add Safari 16.4+ and Firefox 128+ validation if those browsers are within the accepted support contract; the existing Playwright config covers Chromium only.
5. Inspect the final standalone/Docker artifact for `braces` and the actual runtime dependency graph before any production-reachability statement. Keep the security gate failing and the release draft unmerged if the audit or any required migration regression remains unresolved.

This decision records a viable engineering path and explicit blockers. It does not declare the current advisory fixed, approve a browser-support change or fork-maintenance burden, or grant merge/deploy permission.

# Course rewards: eligibility, privacy, and history

Public-track points are a server-owned record of **currently validated learning**, not a measure of posting, commenting, liking, page views, event attendance, or self-reported progress. An eligible learner earns 50 points for one course only when all of these hold:

- The course is explicitly approved by an administrator for the current quiz material.
- The learner is enrolled, is a normal `USER`, is not the course instructor, and is not marked as a test account.
- `completionState(...).complete` is true for every current leaf revision.
- At least one persisted valid quiz leaf has a server-graded passing `QuizAttempt` for that learner and its current content revision.

A persisted valid quiz is available to enrolled learners through the existing course-content route. An empty, malformed, non-leaf, or otherwise ungradable quiz cannot satisfy the approval gate. Course owners can edit content but cannot approve rewards. Administrators can approve or withdraw approval from the courses UI. Approval stores a fingerprint of quiz IDs, content revisions, and leaf status; a material quiz/scoring or tree change clears approval and revokes active points in the same course-content transaction. Quiz title and ordering changes do not clear approval. Other content edits can invalidate current course completion, and active points are reconciled accordingly. A revised quiz needs a current passing attempt and a new administrator approval before points return.

**Historical learning is retained.** `Enrollment.completedAt` records first completion while the course exists. On that validated first completion, `CourseCompletionRecord` saves only the learner ID, course ID/title, and completion time, with no course foreign key. The reward migration backfills this record only from actual completed enrollments. This private milestone survives later edits and course deletion; deleting the account cascades it. Previously issued certificates remain valid after edits. Active public-track points can fall when current learning/approval conditions stop being met; this is a validity change, not a finding of learner misconduct. The private reward summary shows recent course-labeled AWARDED, REVOKED, and REINSTATED changes with reasons and point deltas. Deleting a course records a `COURSE_REMOVED` revocation and retains the ledger's course-title snapshot; deleting an account cascades its ledger and change history.

`RewardLedger` has one unique `(userId, eventType, sourceId)` key per course completion. Repeats and retries keep that key; state transitions increment `stateVersion` and create one change per unique `(ledgerId, version)`. The mutation routes reconcile within their existing serializable transactions. Approval and test-account changes recheck the administrator role inside the transaction and reconcile existing awards before commit. The leaderboard reads active points only for opted-in, non-test `USER` accounts. Opt-in defaults to false; public results contain only name, avatar, and total points, without persistent account IDs. Course IDs, quiz attempts, certificates, and change reasons are available only in the learner's private endpoints.

Course-content creation, update, deletion, reorder and move also verify administrator authority from the stored account inside the same serializable transaction as the content and reward changes. A session validated before a committed demotion or account deletion cannot authorize later quiz changes or revoke learners' rewards. Each serialization retry rereads authority; course owners retain their existing editing permissions. Attaching another owner's local H5P package requires a separate current-administrator check within that transaction, even when the actor owns the destination course. H5P creation no longer performs its only attachment check before the transaction; creation and update both reread package ownership and any required administrator role on retry. These checks only read existing package metadata and never write package files. This is a transaction-snapshot guarantee, not a promise that revocation always wins genuinely overlapping transactions. The real SQLite regression in `__tests__/api/course-content-authorization-db.test.ts` exercises all five routes, preserved progress/ledger/badges on rejection, authorized edits, own/foreign H5P attachments, and rollback followed by demotion before a forced serialization retry. The injected conflict tests retry behavior; live PostgreSQL concurrency remains a release check.

The private course-reward panel shows the next milestone at 1, 3, then 5 distinct server-recorded course completions, with explicit numeric progress and a course-directory link. The count uses durable completion snapshots, so an earlier completed course remains a historical milestone after later course edits; active reward points remain separately reversible. These historical milestones do not award badges, public ranks, streaks or deadline pressure.

Separately, the server now maintains **one current verified-learning badge** (`Badge.id = course-achievement-verified-v1`) for an eligible learner with at least one active course-completion reward. It is not a badge per course or a permanent historical certificate. The same serializable reward transactions create or remove its unique `UserBadge` row when a current passing quiz/completion is awarded, quiz material changes, administrator approval is withdrawn, a course is deleted, or an account becomes ineligible. Repeated and concurrent qualifying attempts retain one award row; revocation of the final active reward removes it, while another active approved reward retains it. The existing `Badge`/`UserBadge` schema supports this single derived award without a migration. No instructor can award it to themselves, and staff and test accounts are excluded.

Members can also opt into **one private learning goal** from Courses: finish 1, 3, or 5 current course-content leaves in 7, 14, or 28 local calendar days. This is a personal planning aid, not a reward source: it has no points, badge, streak, public rank, notification, or penalty. The member selects a target and duration; the server records only the goal, start, timezone, exclusive local-midnight deadline, and optional pause time. Progress is calculated on every read from current, server-authenticated completions after opt-in and before the deadline. A leaf counts only while the member remains enrolled, its current content revision matches the saved completion, and for quizzes a current passing server-graded attempt exists. The member's own courses do not count. A repeated completion does not refresh its timestamp or increment the count. Content edits, removals, unenrollment, or revoked quiz validity can lower the count; the API never accepts a client-supplied count. Private goal routes derive the account from the session and send `private, no-store` responses. Pausing is optional and extends the deadline one day for each local date boundary crossed (including DST); verified learning during a pause still counts. Resuming does not erase progress. Canceling deletes only the goal, not the course progress, and allows a new goal. This separate schema is added in PostgreSQL upgrade `0008_private_learning_goals.sql` and SQLite migration `0009_private_learning_goals.sql` after the actionable-notification migrations.

The badge is available to its eligible owner through the authenticated profile API. Other signed-in members see this learning badge in profile/search responses only when its owner has `publicRankingOptIn = true`; unrelated existing badges keep their previous visibility. Search fetches one extra badge before filtering so hiding the private award cannot displace an unrelated displayed badge. The profile UI renders only the badges provided by that API and explains the learning badge's opt-in visibility to its owner. The public leaderboard still depends only on opted-in active points. No email, push, or external badge delivery is configured.

Schema changes are in PostgreSQL upgrade `0004_reward_ledger.sql` and SQLite migration `0005_reward_ledger.sql`, after the progress and report upgrades. The guarded demo seed explicitly marks Alice and Bob as test accounts when it creates or updates them; migrations leave existing accounts unclassified instead of guessing from an email address. Administrators can explicitly flag legacy test accounts. New accounts default to non-test. A deployment must apply the full ordered, checksummed migration history before starting the new server. Local verification covered fresh SQLite installation, upgrade from a clean main-schema database, repeat no-op deployment, checksum and foreign-key checks, Prisma validation for both providers, unit/UI tests, and authenticated production HTTP flows including concurrent duplicate submissions, quiz revision/reapproval, certificate retention, and deletion cascades. PostgreSQL execution requires a PostgreSQL service in CI or the deployment environment; none was available locally.


Chapter calendar releases control access and new learner work, independently of
already earned credit. A date-only publication retains current-revision progress,
valid assignment grades, reward ledger/badge/pathway credit and their timestamps;
midnight causes no revoke/reinstate transition and needs no scheduler. Authorized
staff may grade an assignment submitted before a later date lock, crediting that
prior work when valid. Changed content, prerequisites, grades, account eligibility
or reward approval still revalidate normally. New certificate issuance additionally
waits for all chapter releases; existing historical certificates remain available.
